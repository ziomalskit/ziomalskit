The resolution selector calculates area using **MPx × 1024 × 1024**, not decimal
million pixels. With canonical aspect ratio `2:3 (Portrait Photo)` and
`multiple=32`, it rounds width and height to multiples of 32. The canonical
`match_reference_size=False`, `custom_width=0`, `custom_height=0` select this
area-driven branch. This control changes target render area, not codec quality
or reference-image preprocessing. AJ accepts finite numeric MPx in **[0.1, 2.0]**;
upstream permits [0.1, 16.0]. AJ's narrower bound is a product input bound,
**not a measured VRAM safety limit**. The frontend suggests increments of 0.1;
the server accepts finite values anywhere in the interval.

Both step controls change the number of returned sampling intervals in
`BasicScheduler`. AJ accepts integers in **[1, 100]**; the pinned upstream node
permits [1, 10000]. First pass retains `res_multistep`, `simple`, `denoise=1`.
Second pass retains `er_sde`, `linear_quadratic`, and the exact serialized
`denoise=0.29999999999999993`. For denoise below 1, upstream calculates
`total_steps=int(steps/denoise)` and keeps the final `steps+1` sigma values.
These are scheduler interval counts, not writer generation budgets. The graph
provides no required ordering constraint between first and second counts;
AJ does not invent one. All three controls are profile-independent graph
parameters. Visual results and suitable choices remain model-dependent.

Higher area materially increases latent dimensions, work and potential VRAM.
More steps increase sampling work/time and may affect Spectrum behavior; CPU
inspection cannot quantify peak VRAM or quality. No control changes frozen
memory/overlap policy or opens admission based on an assumed GPU capacity.
**All nondefault settings require GPU acceptance, which remains pending.**

## Descriptor and trusted engine

`h3/app/workflow_adapters.py` is the generic engine/registry.
`h3/workflow_adapters/h3_v20.json` is the canonical descriptor, schema version 1.
It contains:

- ID, label, immutable baseline filename/size/hash and template contract;
- scoped anchors for renderer, loader fields, Step 3/4 writers, analysis model
  sources, duration/frame expressions, references, audio controls, seeds, LoRAs,
  conditioning bridge, samplers, guiders and final video path;
- exact expected types/modes, ordered widget names and canonical-default hashes,
  input/output names/types/slots/link mirrors, LoRA row keys and proxy interfaces;
- required graph edges, profile-to-widget bindings, explicit analysis model
  replacements, writer/seed routes and render-control bindings;
- API addresses for runtime release/temporal guards and final-output validation.

Anchors are **graph-scoped**, not a flat global node-ID lookup. Widget hashes
also bind canonical duration expressions and distinguish the two writer stages.
Required edge records bind `[id, origin, origin_slot, target, target_slot, type]`.
The descriptor contains no duplicated prompt instructions.

Only the explicit repository registry selects statically imported Python hooks.
There is no plugin discovery, dynamic import, arbitrary uploaded adapter or
browser-supplied path. `h3/app/adapters/v20.py` handles the duration alias rewire,
legacy passthrough removal and unnamed-expression normalization after validation.
`h3/app/adapters/v20_api.py` installs temporal, durable-analysis and release
dependencies. Declarative changes use the generic engine's `apply_profile`,
`apply_duration`, `apply_references`, `apply_audio`, `apply_loras` and
`apply_render_settings`; API preparation calls `install_runtime_guards` and
`validate_final_graph`. Existing v20/production_api imports are compatibility
facades for tools/tests. Legacy diagnostic graph IDs live in
`h3/app/legacy_workflow.py`, outside the production path.

## Fail-closed validation

`load_and_validate()` verifies bytes/SHA first, then **all** required anchors
before any runtime mutation. Missing nodes, wrong types/modes/widgets, changed
defaults/ports/edges, ambiguous IDs, swapped writers, changed LoRA structures or
proxy interfaces raise an explicit `WorkflowAdapterCompatibilityError`.
No nearby-node/title search or mutable-default fallback is allowed.

Runtime UI validation still checks saved widget consistency and the actual
worker catalog. Conversion must consume saved widgets. Phase pruning validates
the approved-prompt resolver, output type and registered output-node flag.
Final adapter validation binds loader routes and resolved render values, verifies
the intended SaveVideo path, frozen duration and conditioning-before-transformer
dependencies. The prompt graph retains both temporal guards, guarded Step 3 →
Step 4 ancestry, native reasoning policy and final-answer-only publication.

The temporal/writer contract is unchanged: **20 s → 481 frames → 20.040 s**;
Step 3 thinking OFF (8192/24576), Step 4 thinking ON (budget 4096,
generation/context 12352/29184), H3 writer 4B and 10Eros writer 9B target.
Natural EOS completion enforcement is untouched.

## Frozen jobs, recovery and browser contract

Before durable batch/job publication, context freezes:

- `workflow_id`;
- `workflow_baseline_sha256`;
- `workflow_adapter_id`;
- `workflow_adapter_schema_version`;
- `workflow_adapter_identity` (SHA256 of canonical descriptor and implementation
  closure, including trusted hooks, conversion/validation, writer/temporal and
  typed render-setting code);
- resolved `render_settings` and `workflow_render_identity` (SHA256 of workflow
  identity plus those resolved values).

These fields are persisted alongside the existing profile/model/provenance,
writer-stage, duration, LoRA and functional memory/overlap identities. Recovery
requires the exact adapter identity and complete frozen settings. Missing fields,
implementation/descriptor drift, a changed profile workflow route or a mismatched
settings hash require **explicit reconciliation**. Old PR #5 queued jobs are not
silently assigned the new adapter. Completed catalogue entries retain their
status and MP4 links even when incompatible; uncertain remote submissions retain
IDs and existing service/lifecycle fences.

Frozen settings never refill from new defaults. Changing a descriptor default
changes adapter identity and requires reconciliation; it cannot rewrite a queued
job. Profile/label/frontend edits likewise cannot change a retry body already
saved in localStorage. The UUID/idempotency contract still binds the exact
incoming request body, including supplied render settings.

`/api/config` attaches `workflow: {id, label, render_controls}` to each trusted
profile. Public controls contain labels, types, defaults, bounds, increment hints,
group and help; no node/widget addresses. The frontend renders the quality group
in the normal form and the remaining controls under collapsed **Advanced render
settings**. Unsupported controls are absent. The server accepts only the typed
`RenderSettings` vocabulary, rejects unknown fields, paths, IDs, strings,
booleans, null, nonfinite numbers, fractional steps and out-of-range values, and
checks adapter support independently of the browser. No arbitrary widget dict
is accepted. LocalStorage retries keep the original exact settings body.

## Adding a future workflow

1. Separately authorize, freeze and checksum its real baseline. Inspect its
   authoritative graph and backend definitions; do not infer settings by title.
2. Add one reviewed repository descriptor with scoped structure/edge assertions,
   verified control defaults/ranges and production input/output contract.
3. Register its ID and any statically imported hook at the trusted dispatch point.
   Use declarative bindings first; add a hook only for a necessary transformation.
4. Point a separately reviewed profile at that ID. Extend the typed request
   vocabulary only for verified controls; derive the UI from backend capabilities.
5. Add CPU corruption, canonical-default parity, typed security, frozen recovery
   and actual-JavaScript retry tests. Treat identity changes as explicit
   reconciliation, never automatic migration. Then perform separate GPU acceptance.

## Validation boundaries and remaining blockers

CPU tests cover structural compatibility, 22 pre-refactor canonical-JSON parity
comparisons, control isolation/conversion/bounds, persistence/recovery drift,
browser security and capability-driven rendering/submission/retry. Required
checks are `make setup`, `make test`, `make audit`, plus the focused adapter and
frontend suites. Historical migration/archive and the canonical attachment must
remain byte-identical.

CPU PASS does not establish actual model loading, pinned live `/object_info`,
video quality/duration, render cost, VRAM coexistence or GPU safety at any setting.
The DavidAU 9B provenance/BF16 build/load/generation blocker remains unchanged.
No Vast/GPU operation or PR merge is part of this feature.
